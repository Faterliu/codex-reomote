## 2. 核心逻辑

### 2.1 分支边界用真实 `turn.id`

```ts
const params: ThreadForkAtTurnParams = { threadId, lastTurnId };
const response = await client.request<ThreadForkResponse>("thread/fork", params);
```

`lastTurnId` 指向的那一轮**包含**在新分支里，之后的轮次不进入新分支。

### 2.2 每轮只出现一个分支入口

`flattenTurns` 在把 turn 展开成 timeline 时统一计算锚点：

- `turnStatus`：每条 entry 都带上所属 turn 的状态；
- `canFork`：仅当 `turn.status === "completed"` 且该 item 是本轮**最后一条 agentMessage**（也就是复制按钮所在的那条 Codex 回复）时为真。

因此 reasoning / command / fileChange / 中间 agent message 都不会出现分支按钮；`inProgress` / `failed` / `interrupted` 一律不提供入口。UI 侧只读 `entry.canFork`，不在 JSX 里堆条件。

### 2.3 点击后的流程

```
点击 [分支]
  → 检查连接状态 → 防重复点击（forkingTurnId 互斥）
  → thread/fork { threadId, lastTurnId }
  → 按 thread.id 去重合并进会话列表（response 与 thread/started 通知共用同一条路径）
  → 复用既有 openThread()：thread/resume 取权威模型/思考程度 + 拉取分页历史
  → 自动进入新 Thread，输入框立即绑定新 thread.id
```

失败时只上报错误，不动原会话：原 `selectedThread`、消息历史、连接状态都保持原样。

### 2.4 去重复用既有机制

`thread/started` 通知原本就按 `thread.id` 过滤去重（`notifications.ts`）；新增的 `upsertThread` 采用同样的「同 id 覆盖、不同 id 才插入」语义，没有引入第二套去重逻辑，也没有无条件 `unshift`。

### 3.2 `thread/fork` 真机协议语义（已通过，对着本机运行中的 app-server 实测）

用原始 WebSocket 客户端连 `ws://127.0.0.1:4500`（token 取自 `%USERPROFILE%\.codex\app-server\mobile.token`，未写入仓库），对一个多轮会话从**第 2 轮**发起 fork：

```
sourceThreadId      01a08f73-7944-74c1-9bed-dc3b80556506
boundaryTurnId      01a08f75-3378-7160-912e-4c1522c4d622   （第 2 轮，completed）
forkedThreadId      01a09e12-601c-7e91-9021-4a94dec2cb3e
forkedFromId        01a08f73-7944-74c1-9bed-dc3b80556506   ← 与原会话一致

checks
  newThreadIdIsDifferent      true
  forkedFromIdMatchesSource   true
  historyTruncatedToBoundary  true   （新线程恰好 2 轮）
  turnIdsMatchPrefix          true   （前 2 轮 turn.id 与原会话逐一相同）
```

新线程的 `thread/turns/list` 只返回前 2 轮，状态保持 `completed`；原会话未受影响。测试产生的分支已用 `thread/delete` 删除。

### 3.3 分支锚点规则（已通过，12 项断言全绿）

把仓库真实的 `threadFormat.ts` 编译后用 Node 跑构造数据断言：

- completed 轮：锚点恰好 1 个，落在最后一条 Codex 回复上，`turnId` 正确；
- inProgress / failed / interrupted：锚点 0 个，`turnStatus` 正确透传；
- 没有 Codex 回复的 completed 轮：不留锚点；
- 多轮混合（completed → inProgress → completed）：锚点分布为 `turn-a`、`turn-c`，不串轮。

**Android 真机上的实际点击交互未验证**，包括按钮实际渲染位置、`hitSlop` 手感、Toast 展示、以及 fork 后输入框是否如期指向新会话。仓库当前无移动端运行时测试框架，JS 层只能做到上述静态与运行时断言。

## 4. 尚存风险

1. **协议生成版本落后于本机 Codex（重要）**
   本机 `codex-cli 0.153.4` 的 `thread/fork` 支持 `lastTurnId`，但仓库 `packages/protocol` 是更早版本生成的，`ThreadForkParams` 里没有这个字段。
   实测直接 `pnpm protocol:generate` 会带来 **112 个文件的协议差异**，并让 9 处**与本次功能无关**的代码类型报错（`rateLimitFormat` 的 `PlanType` / `GetAccountRateLimitsResponse`、`RateLimitSnapshot.spendControlReached`、`threadFormat` 的 `functionCallOutput` 分支、`imageGeneration` 新增 `failure` 字段）。
   为不把无关改动混进提交，本次**没有**重新生成协议，而是在 `api.ts` 里用一次性交叉类型补上缺字段：

   ```ts
   export type ThreadForkAtTurnParams = ThreadForkParams & { lastTurnId: string };
   ```

   代价：客户端其余协议类型仍停留在旧版本，长期需要单独安排一次协议同步 + 修那 9 处报错。

2. **错误码不可区分**
   `jsonRpcClient` 只把 `error.message` 包成 `Error`，丢掉了 JSON-RPC `code`。因此「RPC 不支持（-32601）」和「当前轮次仍在执行」是靠关键字匹配文案来判断的，不是靠错误码。如果 app-server 改了错误措辞，会落回「创建分支失败，请稍后重试」。

3. **fork 后复用 `thread/resume`**
   分支创建后沿用了既有的打开会话流程（`thread/resume` + `thread/turns/list`），而不是只吃 `thread/fork` 的返回值。
   好处是模型/思考程度、历史分页都拿到权威数据，且 `thread/fork` 返回的 `thread.turns` 在长会话下可能被 server 截断；风险是与 app-server 的 `active writer` / listener attach 状态可能有交互，这一点未在真机确认。若真机上出现分支会话状态异常，可先改为直接使用 fork response 的 `thread.turns`。

4. **发送锁定只在分支创建期间**
   `fork 期间` 发送按钮禁用、占位提示「正在创建分支…」；分支创建完成（`openThread` 返回）后立即解锁。没有额外的「selectedThread 已落定」二次确认。
